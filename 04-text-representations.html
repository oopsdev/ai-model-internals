12. Tokenization — 把文字變成 token

模型吃的是數字、不是字。Tokenization 把文字切成 token、每個 token 對應一個 id，再查 embedding（§13）：

$$\text{文字}\to\text{tokens}\to\text{ids}\to\text{embeddings}\to\text{模型}$$

切分結果依 tokenizer 而定。 本節所有切分都只作示意：實際 token 取決於所用的 tokenizer、vocabulary、文字前後空白及訓練語料。同一段文字換一個模型，切法與 token 數都可能不同。

四種基本切分單位：

單位基本元素特性
character（字元）Unicode 字元詞表小、序列長；詞表沒收錄的字元仍可能變成 [UNK]
byte（位元組）UTF-8 編碼後的 byte（共 256 種）任何字串都能表示、不會有未知字元；序列最長
subword（子詞）以 BPE、WordPiece、Unigram 等方法學出的片段常見詞整塊、罕見詞拆片段，折衷詞表大小與序列長度
byte-level BPE從 byte 出發做 BPE 合併兼有子詞的效率與 byte 的完整覆蓋；不等同從 Unicode 字元出發的 BPE
  • 為什麼多數 LLM 用子詞：整詞當單位 → 詞表爆炸又處理不了新詞；單字元或 byte → 序列太長、運算成本高。子詞折衷：常見詞當一個 token、罕見詞拆成片段。

英文 token（子詞）例子（示意）。 在常見的英文子詞 tokenizer 中，常見「詞」常是 1 個 token；長詞 / 罕見詞才拆成子詞：

英文切成 token（示意）個數為什麼
cat、thecat／the1常見詞 → 整塊
tokenizationtoken + ization2拆詞根 + 詞綴
unhappinessun + happi + ness3前綴 + 詞根 + 後綴
lowestlow + est2共用詞綴 est
ChatGPTChat + G + PT（另一詞表可能是 Chat + GPT）2~3新詞 / 專有名詞依詞表拆成不同片段

中文 token 例子（示意）。 中文沒有空白斷詞；常見字 / 詞在詞表中可能是 1 個 token。詞表沒收錄的字，在 byte-level tokenizer 中會退回成多個 UTF-8 byte 片段（常用中文字在 UTF-8 中佔 3 bytes）：

中文切成 token（示意）個數為什麼
的、我的／我1高頻字 → 1 token
我們我們（或 我+們）1~2常見詞可能整塊
深度學習深度 + 學習（或逐字）2~4詞 / 字混合
龘（生僻字）多個 byte 片段2~3詞表未收錄 → 退回 byte

語言間的 token 效率依 tokenizer 而異。 若詞表對中文的覆蓋較少，同樣語意的中文可能比英文用更多 token；針對中文擴充詞表的 tokenizer，則可能相近甚至更少。因此不能只用字數推估成本或 context 用量，要用目標模型的 tokenizer 實際計數。

BPE（Byte Pair Encoding）怎麼切。 BPE 原是資料壓縮演算法，用在 tokenizer 時：從基本單位出發，反覆把「出現頻率最高的相鄰配對」合併成新單位，直到詞表達到設定大小。基本單位有兩種——character-level BPE 從 Unicode 字元開始，byte-level BPE 從 UTF-8 byte 開始。以下用 character-level 示意，語料 low, lower, lowest, newest, widest…：① 最常見對 e+s → es；② es+t → est；③ l+o → lo、lo+w → low。學出的子詞 low、est、new… 於是 lowest=low+est。好處：常見詞 → 短序列、罕見 / 新詞 → 可組合的片段。是否還會出現未知詞 (OOV) 要看 tokenizer：byte-level BPE 或具 byte fallback 的 tokenizer 能把任何字串退回 byte 表示，因此不會 OOV；只用字元或子詞詞表、又沒有 fallback 的 tokenizer，遇到未收錄字元仍會產生 [UNK]。

工程意涵。 token 數 = 成本單位——LLM API 計費、context 長度限制都以 token 計。每個字或詞耗用幾個 token 依 tokenizer 與語言而異；估算成本時，用目標模型的 tokenizer 對實際文本計數。

13. Embedding 與向量表示

Embedding = 把離散符號（token / 詞 / 類別 / 物件）或輸入片段映成連續向量。 承接 §12：token 拿到 id 後，靠 embedding 查表變成向量餵進模型；訓練、推論、生成三階段都用到（不是只有生成才需要）。

不只文字：類別特徵（如城市、裝置型號）與位置資訊也常用 embedding。影像本身已是連續數值、不必查表，但 Vision Transformer 會把影像切成 patch，再線性投影成 patch embedding。

名稱（中譯）。 Embedding 中譯為嵌入（完整常說詞嵌入 word embedding、嵌入向量），也意譯為向量表示。取 embed（鑲嵌、把東西放進某結構）之意——把離散符號嵌入一個連續的向量空間：原本像「貓」「狗」這種符號彼此無法算距離，嵌入後各變成空間中的一個點（向量），就能量距離、比相似度。這也呼應數學上的嵌入映射（把一個空間嵌進另一個、並保留原有關係）。

「embedding」一詞常指四種不同的表示，要分開看：

類型輸入 → 輸出怎麼得到典型用途
Lookup embedding（§13.1）token id → 一個向量查表矩陣 $E$ 的一列；訓練學出模型第一層的輸入
Contextual representation（§13.2）某句中的一個 token → 一個向量Transformer 中間層的 hidden state，隨上下文而變模型內部運算、下游微調
Sequence embedding（§13.3）整句 / 整段 → 一個向量對 hidden states 做 pooling（平均、取特殊 token 等）分類、分群、句子相似度
Retrieval embedding（§13.4）query / 文件 → 一個向量以檢索目標（如對比學習）專門訓練的 sequence embeddingRAG、語意搜尋

13.1 Lookup embedding：token id 查表

  • 怎麼來：一張可學的查表（embedding 矩陣 $E$，大小 $V\times d$，$V$ 詞表大小、$d$ 維度）；token 的 id 就是「取第 id 列」。同一個 id 永遠查到同一個向量，與上下文無關。
  • 幾何意義：向量活在一個空間裡，可用餘弦相似度比較方向（§1.4）。訓練後，常出現在相似語境的 token 向量往往較接近——這是訓練目標造成的傾向，不是查表本身保證的性質。

具體例子（示意向量）。 真實 embedding 多為數百~數千維，這裡用每維都代表一個特徵的小向量示意。假設三個維度（特徵）代表「是動物 / 是交通工具 / 會移動」：

詞示意向量 (是動物, 是交通工具, 會移動)
cat(0.9, 0.0, 0.6)
dog(0.9, 0.0, 0.7)
car(0.0, 0.9, 0.8)
bus(0.0, 0.9, 0.7)

比「像不像」用餘弦相似度（§1.4）：

詞對餘弦相似度解讀
cat vs dog≈ 0.997都是動物 → 幾乎同向
car vs bus≈ 0.998都是車 → 幾乎同向
cat vs car≈ 0.37不同類 → 夾角大、相似度低

語意向量加減（靜態詞向量的經典例）。 在 Word2vec、GloVe 等靜態詞向量中，曾觀察到如下類比（維度取「皇室程度, 女性程度」示意）：

$$\underbrace{(0.9,\,0)}_{\text{king}}-\underbrace{(0.1,\,0)}_{\text{man}}+\underbrace{(0.1,\,1)}_{\text{woman}}=(0.9,\,1)\approx\underbrace{(0.9,\,1)}_{\text{queen}}$$

把「man → woman」的方向（＝加上「女性」）平移到 king 上，結果就落在 queen 附近。這是歷史上展示「語意關係可被編碼成方向」的經典例子；不代表所有現代 embedding（尤其 contextual 或 retrieval embedding）都呈現同樣的線性類比。

這些向量的值怎麼來（怎麼算出來的）？ 不是用公式算的，而是訓練學出來的參數：

  • 一張查表矩陣 $E$（大小 $V\times d$）；這 $V\times d$ 個數字全是參數。
  • 隨機初始化 → 梯度下降更新：一開始是小亂數；之後跟模型其他權重一樣，前向「token → 查 $E$ → 進模型 → 算損失」，反向把 $\partial L/\partial E$ 回傳、往降低損失的方向調每個值（§9 反向傳播、§5 梯度下降）。大量更新後收斂成有用的向量。
  • 學習信號來自任務：Word2vec 用「預測上下文詞」、LLM 用「預測下一個 token」。常出現在相似語境的詞（貓 / 狗），為了預測得準，向量常被學得相近——這是訓練的副產品，不是人為設定。
  • 重要澄清：前面「是動物 / 是交通工具」只是示意。真實 embedding 每一維沒有人為指定意義，是訓練中自己長出來的抽象方向；單看一維通常無法解讀，是整個向量的方向與組合承載資訊。

維度 $d$（向量有幾格）怎麼定？是超參數，訓練前就固定。 訓練學的是向量裡的值（$V\times d$ 個數字），但維度 $d$ 本身固定不變，不是訓練中長出來、也不是最後才決定的。這是「參數 vs 超參數」的區別：

  • 參數 (parameters)：訓練時自動學的（embedding 的值、各層權重）。
  • 超參數 (hyperparameters)：訓練前人為設定的（維度 $d$、學習率 $\eta$、層數、batch size…）。
  • $d$ 怎麼挑：靠經驗 + 實驗（調參）。常見 Word2vec / 小模型 100~300、BERT 768、大型 LLM 上千~上萬（GPT-3 達 12288）。太小 → 裝不下資訊、表達力不足；太大 → 參數暴增、算力 / 記憶體貴、易過擬合、邊際效益遞減。實務是試幾個值、看驗證集（§6）選 CP 值最好的——屬外層調超參數的實驗迴圈（訓練好幾次比較），不是單次訓練內學出來的。

13.2 Contextual representation：同一 token、不同上下文

  • Lookup embedding 對同一個 token id 永遠給同一個向量；進入 Transformer 後，每一層的注意力會混入上下文（§15），輸出的 hidden state 因此隨句子而變。
  • 例：「蘋果很好吃」與「蘋果發表新手機」中的「蘋果」，lookup 向量相同，但中後層的 hidden state 不同——前者較接近水果的用法、後者較接近公司的用法。
  • 這些 hidden state 是模型內部的中間表示；LLM 最後一層的 hidden state 再經 LM head 轉成 vocabulary logits（§15、§16）。

13.3 Sequence embedding：把整句壓成一個向量

  • 要比較兩句話，需要一句一個向量。常見做法：對所有 token 的 hidden state 取平均 (mean pooling)，或取特殊 token（如 BERT 的 [CLS]）的 hidden state。
  • 直接拿未經專門訓練的語言模型做 pooling，句子相似度的品質常不理想；實務多用專門訓練過的句向量模型。

13.4 Retrieval embedding：為檢索而訓練（RAG 的核心）

  • 以檢索目標訓練：常用對比學習 (contrastive learning)，讓「query 與相關文件」的向量接近、與不相關文件的向量拉遠。有的模型對 query 與文件使用不同的前綴指令或編碼器。
  • RAG 流程：把文件段落與查詢都 embed 成向量，用餘弦相似度（或內積）找最相關段落 → 餵給 LLM 生成答案。也用於語意搜尋、推薦、去重。
  • 「意思相近 → 向量相近」在這裡是明確的訓練目標；對 lookup embedding 而言只是訓練後的傾向（§13.1）。
  • query 與文件必須用同一套 embedding 系統編碼（同一個模型，或成對訓練的 query / 文件編碼器），並依該模型規定的前綴或前處理，向量才能互相比較。

工程意涵。 RAG 靠 retrieval embedding 檢索；實務用向量資料庫存百萬級向量、做快速最近鄰搜尋。檢索品質很大程度取決於 embedding 模型是否符合你的語言、領域與查詢型態，應以自己的資料評估（如 recall@k，§18.3）。

14. RNN / LSTM — 序列建模

有了 token 的向量序列（§12、§13），接著要有能處理序列的模型。序列資料（文字、時序、封包大小序列）有順序、長度不定，FC/CNN 不擅長。RNN（循環神經網路）用一個隱藏狀態 $\mathbf{h}$ 當「記憶」，逐步吃輸入、更新記憶：

$$\mathbf{h}_t=\sigma(\mathbf{W}_h\mathbf{h}_{t-1}+\mathbf{W}_x\mathbf{x}_t+\mathbf{b})$$

每一步把「上一刻的記憶 $\mathbf{h}_{t-1}$」和「這一刻輸入 $\mathbf{x}_t$」混合成新記憶，可再輸出。

  • 問題：長距依賴。序列一長，沿時間展開就像很深的網路 → 梯度消失/爆炸，記不住遠處資訊。
  • LSTM / GRU：加閘門 (gate) 控制「記住 / 遺忘 / 輸出」多少 → 能記更久，是長序列的主力（Transformer 出現前）。

14.1 哪些應用適合用 RNN（為什麼）

跟 CNN 一樣，RNN 適不適合取決於資料是否符合它的內建假設——RNN 假設資料是有順序的序列，且當下輸出依賴歷史。

RNN 的內建假設適合的資料 / 問題特徵為什麼例子
順序性（逐步吃輸入）資料有時間 / 先後順序，順序有意義隱藏狀態沿時間傳遞時序、文字、語音、封包序列
可變長度（同參數跑到底）輸入長度不定每步共用同一組權重長短不一的句子、連線 session
時間上參數共享同一種規律不分位置都成立每個時刻用同一 $\mathbf{W}$週期性訊號、重複語法
狀態 / 記憶當下輸出依賴前文脈絡$\mathbf{h}$ 累積歷史資訊依上下文預測下一字 / 值
因果 / 串流資料逐步到達、要邊來邊反應由左到右一步步算即時語音、線上異常偵測

適合的應用：時序預測（感測器、網路流量 metrics、股價）、語音辨識、手寫辨識、log / 封包序列異常偵測、串流 / 即時逐步處理；文字生成（早期，現多被 Transformer 取代）。

不適合 / 侷限（對照）：

  • 很長的序列、需長距依賴 → 梯度消失（即使 LSTM 也有極限）、記不住遠處 → 用 Transformer / 注意力（§15）。
  • 需大量平行訓練 → RNN 逐步串行、難平行、訓練慢 → Transformer 可整段平行。
  • 無順序關係的資料（表格、影像空間結構）→ 順序假設失效 → 用 MLP / 樹模型 / CNN。

工程意涵。 網路 AI 的序列任務（封包序列、時序 metrics）用 1D-CNN / LSTM 就夠、輕量、又天生串流友好，適合邊緣即時；但一旦需要長距依賴或大規模平行，語言與長序列已被 Transformer 取代（留中央）。
