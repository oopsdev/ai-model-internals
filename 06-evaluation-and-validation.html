18. 評估指標數學

「準確率高」不一定好——挑對指標比挑模型更關鍵。

先回答一個常見問題：有沒有「一個值」代表模型訓練的好壞？ 有，但要分清是哪個值、在哪份資料上算：

  • 損失 (loss)：訓練時直接最小化的目標值（§3），越低代表越貼合資料。但只看「訓練集損失」會被過擬合騙（訓練集很低、真實表現卻差）。
  • 評估指標 (metric)：把「好壞」翻成人看得懂的分數，依任務不同（見下 §18.1–§18.3）——分類看 accuracy / F1 / AUC、迴歸看 MSE / R²、LLM 看 perplexity、檢索看 Recall@k。
  • 關鍵：要在「沒看過的資料」上算才算數。 真正代表模型好壞的，是驗證 / 測試集（§6）上的損失或主要指標；實務會同時看「訓練 vs 驗證」兩條損失曲線來判斷過擬合（§6）。

一句話：訓練過程看「損失」、評模型好壞看「驗證 / 測試集上的主要指標」；沒有放諸四海皆準的單一值，要依任務挑對指標。

18.1 分類

先定「正類 (positive)」＝ 你要偵測的目標類（本節以惡意 / 攻擊為例，其餘為負類＝正常）；四格由「實際 × 預測」交叉：TP 實際正、也判正（抓對惡意）；FP 實際負、卻判正（正常被誤判＝誤報）；FN 實際正、卻判負（惡意被放走＝漏抓）；TN 實際負、也判負（判對正常）。一切指標都由這四格算出。

命名規則（別看錯）：第 2 字母＝模型「預測」的類（P 正 / N 負）、第 1 字母＝那個預測「對不對」（T 對 / F 錯）——與「實際是哪一類 / 在哪一列」無關。所以對角線 TP、TN 都是猜對 (T)、反對角線 FP、FN 都是猜錯 (F)。例：右上格 FN ＝「模型預測負 (N)、但猜錯 (F)」＝ 實際正卻判負 ＝ 漏抓（不是 TN——因為它猜錯了）。

  • Accuracy（正確率） $=\frac{TP+TN}{\text{全部}}$：全部猜對的比例；不平衡時會騙人（99.9% 正常，全猜正常也 99.9%）。（注意別和下面的精確率 precision 混——兩者不同。）
  • Precision（精確率） $=\frac{TP}{TP+FP}$：「判為正類的裡面，真的是正類的比例」（此處：說是惡意的，有多少真的是）——誤報 (FP) 越少，Precision 越高（FP 在分母）。
  • Recall（召回率） $=\frac{TP}{TP+FN}$：「真正類裡，被抓到的比例」（此處：真惡意的，抓到多少）——漏抓 (FN) 越少，Recall 越高（FN 在分母）。
  • F1（正式名 F1 score / F1-measure） $=\frac{2PR}{P+R}$：precision 與 recall 的調和平均（是 $F_\beta$ 在 $\beta=1$ 的特例；$\beta>1$ 偏重 recall、$<1$ 偏重 precision）。它算的是「單一類別 / 二元」的分數——同時要求少誤報 (P) 與少漏抓 (R)，任一低則 F1 低，比 accuracy 適合不平衡。用途:二元偵測（惡意/正常）、以及多類裡的逐類評估。
  • ROC / AUC：調不同門檻畫出的曲線 / 曲線下面積，衡量整體區辨力。類別不平衡時與 PR-AUC 的差異、機率校準與門檻選擇流程見 §18.4。
  • 多類別怎麼把各類 F1 合成一個?（平均方式——macro-F1 就是從這來的，不是 F1 的別名）：先對每類各算一個 F1，再合成成一個總分:
    • macro-F1：各類 F1 等權平均——少數類也算數，類別不平衡時最該看；
    • micro-F1：把所有類的 TP/FP/FN 匯總後才算一個——由多數類主導；
    • weighted-F1：各類 F1 按樣本數加權平均。
    多類情境只說「F1」會有歧義，務必指明用哪種平均（實務常用 macro-F1；用途:報一個跨類總分又不想被多數類蓋過）。搭配 per-class floor：除了 macro-F1，另看「每類 F1 的最低者」，別讓平均掩蓋弱類（分開判定）；有群組結構再考慮分組加權避免大群組主導（§19.2）。

怎麼看出「哪一類爛、哪兩類互相混」（多類診斷）。 別只看一個總分，做兩件事（以 3 類「正常 / DoS / 掃描」為例）：

① per-class 表 → 找最爛的類。 每類各算 precision / recall / F1：

分數要多高才算「可用」?（沒有固定門檻，要看脈絡） 沒有「F1 > 0.9 就算好模型」這種普世線——同一個 0.90 在某任務是頂標、在另一任務是不及格。判斷「可用」看四件事：

  • 先比基準 (baseline)：baseline ＝ 一個「陽春、不費力」的參照（不學習、或最簡單的模型 / 規則），當比較的起點與及格線。常見的有——多數類基準（永遠猜最常見的類；不平衡時全猜多數類的 accuracy）、隨機、簡單規則 / 邏輯迴歸 / 單棵樹、現有系統 / 前一版 / 人工的表現；迴歸的 baseline 是「永遠猜平均值」（對應 R²＝0，§18.2）。模型的價值 ＝ 它比 baseline 高多少（lift ＝ 模型 − baseline），不是它的絕對分數；至少要明顯贏過基準才有意義（99.9% 正常時，99.9% accuracy 等於沒做事）。
  • 錯誤成本 → 決定看哪個指標、門檻訂多少：漏報 (FN) 與誤報 (FP) 代價常不對等。資安 / 醫療漏報代價高 → 要求 recall 高（如 recall ≥ 0.95）；誤報擾民 → 要求 precision 高。門檻應由業務 / 營運需求反推（例：「recall ≥ 0.95 且 precision ≥ 0.8」），不是拍腦袋定 0.9。
  • 不平衡下別看 accuracy：改看 per-class recall / precision、PR-AUC、macro-F1、每類 F1 的最低者（見上、§19.2）。
  • 分數是「樣本估計」、要看信賴區間與顯著性：$F1=0.91$ 只是這批測試資料的估計，換一批會變；要問「贏過基準 / 對手是真的，還是抽樣雜訊?」——用 bootstrap CI、配對檢定（§19）。且分類門檻 (threshold) 要在 validation set 選，不能拿 test set 挑（否則高估）；完整流程見 §18.4。

一句話：「可用」不是看某個絕對分數，而是「明顯贏過合理基準 ＋ 滿足由錯誤成本反推的業務門檻 ＋ 統計上站得住腳」三者兼具。

18.2 迴歸

MSE / MAE：均方 / 平均絕對誤差（§3、§1.4）；R²：模型解釋了多少變異。

18.3 生成 / 檢索

  • Perplexity（困惑度）：語言模型「對下一字有多不確定」，越低越好（＝負對數似然的指數，§2、§16）。
  • BLEU / ROUGE：比生成文字與參考答案的重疊。
  • Recall@k：檢索前 $k$ 個有沒有命中正確段落（RAG 檢索品質）。

18.4 機率品質與門檻選擇

分類器多半先輸出分數或機率，再用門檻轉成類別。評估要分兩層：排序好不好（AUC），以及機率準不準（校準）；門檻則是最後依成本決定的一步。

ROC-AUC vs PR-AUC（類別不平衡時）。

  • ROC 曲線橫軸是 FPR $=\frac{FP}{FP+TN}$。負類極多時 TN 很大，即使誤報 (FP) 的絕對數量不少，FPR 仍很小，ROC-AUC 容易看起來偏樂觀。
  • PR 曲線看 precision 與 recall，只關心正類；隨機模型的 PR-AUC 約等於正類比例（例如正類占 1% 時約 0.01），而不是 0.5。
  • 不平衡任務建議兩者都報，並註明正類比例，PR-AUC 才有比較基準。

機率校準 (calibration)：「說 0.8 的，實際約八成是正類嗎？」

  • 模型可能排序很好（AUC 高），但機率系統性偏高或偏低。類別加權、過採樣、強正則化等訓練設定都可能讓輸出機率偏離實際頻率。
  • Brier score $=\frac1N\sum_i (p_i-y_i)^2$：預測機率與 0/1 結果的平方差，越低越好；同時反映區辨力與校準。
  • ECE（Expected Calibration Error）：把預測機率分成 $M$ 個區間，比較每個區間的平均預測機率 $\bar p_b$ 與實際正類比例 $o_b$：$\text{ECE}=\sum_{b=1}^{M}\frac{n_b}{N}\,|o_b-\bar p_b|$。數值會受分箱數與分箱方式影響，報告時要註明。
  • Reliability diagram（可靠度圖）：橫軸為各區間的平均預測機率、縱軸為實際正類比例；點落在對角線上表示校準良好；落在對角線下方表示預測機率高於實際比例（高估）。過度自信的模型通常在高機率區落在下方、低機率區落在上方。
  • 校準方法：Platt scaling（擬合一個 sigmoid）、isotonic regression、temperature scaling（NN 常用）。校準器要在 validation set 上擬合，不可用 test set。

門檻選擇的完整流程：

  1. 在 training set 訓練模型（必要時在 validation set 上校準）。
  2. 在 validation set 上取得分數，依需求選門檻：
    • 成本最小化：最小化 $c_{FP}\cdot FP + c_{FN}\cdot FN$（兩種錯誤的代價由業務決定）；
    • recall floor：在 recall ≥ 目標值（如 0.95）的門檻中，取 precision 最高者；
    • precision floor：在 precision ≥ 目標值的門檻中，取 recall 最高者。
  3. 凍結門檻（連同模型與前處理）。
  4. 在 test set 上只做一次最終評估，報告該門檻下的指標與信賴區間（§19.4）。看過 test 結果再回頭調門檻，原結果就不再是無偏估計。

多類別與多標籤的差異：

任務AUC 怎麼算門檻怎麼定
多類別（每筆恰屬一類，softmax，§3.3）one-vs-rest（每類對其餘）或 one-vs-one 各算 AUC，再 macro / weighted 平均；需註明用哪種通常取機率最大的類（argmax）；成本不對等時可用成本矩陣或調整各類權重
多標籤（每筆可同時屬多類，各自 sigmoid，§3.2）每個標籤各算一個 AUC，再 macro / micro 平均每個標籤各自選門檻，各自依成本或 floor 決定

工程意涵。 資安場景高度不平衡——別看 accuracy，要看 recall（抓到多少真威脅）與誤報率；門檻可用機率分數調（見 §2 工程意涵）。RAG 檢索品質看 Recall@k。

19. 模型驗證與統計嚴謹性

前面各章教「模型如何學」；這章教「如何嚴謹評估、並敢相信一個模型」——這是從實驗室到上線最容易出錯、也最能自欺的一環。核心原則:先定義「失敗長什麼樣」、把檢查寫成可執行、凍結協定，再看資料。

19.1 為什麼「隨機切分 + 看準確率」會騙人

過擬合（§6）只是冰山一角；更隱蔽的是離線分數漂亮、上線卻垮。三大自欺來源:資料洩漏（19.3）、混淆變數（19.5）、資料窺探（19.5）。嚴謹評估就是逐一把它們鎖死——否則 F1 再高也不可信、且事後補不回來。

19.2 交叉驗證 (Cross-Validation)

  • k-fold CV:把資料切 $k$ 折，輪流拿一折當驗證、其餘訓練，平均 $k$ 次 → 比單一驗證集更穩、更省資料。
  • 分組交叉驗證 (Grouped CV) — 最關鍵:資料有群組結構（同使用者/同 session/同來源/相鄰時窗高度相關）時，重採樣單位必須是「群組」而非「單筆」。否則同群組同時落在 train 與 test，模型是「認得這群組」而非學到規律 → 分數虛高。要選「最上層的獨立生成事件」當重採樣最小單位（同一原始檔切出的 N 片只算 1 個獨立樣本）。
  • nested CV（巢狀）:內層 CV 調超參數、外層 CV 估效能，避免「同一份資料又選模型又報成績」的樂觀偏差。
  • held-out 泛化評估:刻意把某來源/裝置/時間段完全排除在訓練外，測分布外泛化（domain / temporal generalization）——比同分布 CV 嚴格、更接近上線。

兩個「gap」別混淆。 泛化落差 (generalization gap) ＝ 訓練集 − 測試集（同分布），量的是過擬合（§6）；遷移落差 (transfer gap) ＝ 來源域 − 目標域（不同來源/裝置/時間），量的是跨分布泛化——held-out 評估量的就是它。上線環境幾乎不同分布，所以真正決定好壞的常是 transfer gap，而非同分布的漂亮分數（分布漂移見 附錄 H）。

19.3 資料洩漏的種類 (Data Leakage)

洩漏 = 訓練時偷看到「上線拿不到」或「等於答案」的資訊，使離線分數虛高。三種常見:

  • 目標洩漏 (target leakage):特徵直接或間接含了答案，或用了推論當下拿不到的資訊。
  • 群組洩漏 (group leakage):同群組跨 train/test（見 19.2）——最常被忽略。
  • 時間洩漏 (temporal leakage):用未來資料預測過去；時間序列必須按時間切。
  • 防治口訣:對每個特徵問「上線當下拿得到嗎?會不會等於答案?」；切分按群組 / 按時間。

19.4 統計推論:別把「一個數字」當結論

測試集有限，$F1=0.91$（定義見 §18.1）只是樣本估計——換一批資料會變。要問「這差異是真的，還是抽樣雜訊?」

  • 信賴區間 (Confidence Interval, CI):給估計一個範圍（如 95% CI），而非單點；CI 很寬 → 別下結論。
  • Bootstrap（自助法）:對測試資料有放回重抽樣很多次、每次重算指標 → 得到指標分布 → 估 CI。它不需假設特定的參數分布（如常態），但仍有前提:樣本要能代表母體，且重抽單位必須是彼此獨立的單位。有群組結構時用 cluster bootstrap（以群組為重抽單位）；有時間相依時用 block bootstrap（重抽連續區塊）。樣本很少或指標接近 0 / 1 時，CI 也可能不準。
  • 兩個不同的問題，用不同的檢定:
    要回答的問題方法
    資料中是否存在可學的訊號？（模型是否勝過「標籤與特徵無關」的情況）標籤置換檢定 (label permutation test):把標籤隨機打亂、重新訓練並評估多次，得到「沒有訊號」時的 null 分布；真實分數若明顯落在 null 之外 → 有訊號
    在同一測試集上，模型 A 是否優於模型 B？配對方法:paired bootstrap（每次重抽同一批樣本，算 A − B 的差，取其 CI）；McNemar test（只看兩模型「一對一錯」的樣本數，適用分類正確率）；配對 permutation test（逐樣本隨機交換 A、B 的預測，得到差異的 null 分布）。依指標選擇相應的配對設計
    標籤置換檢定只能說明「有沒有訊號」，不能用來判斷兩個模型誰比較好。
  • 假設檢定 / p-value:在虛無假設與檢定前提都成立時，觀察到與目前統計量至少同樣極端的結果的機率。它不是「虛無假設為真的機率」，也不是「結果只是運氣的機率」；p 值小只表示資料與虛無假設不太相容，不代表效果大（要看效果量與 CI）。多次比較時還要校正（如 Bonferroni、Holm）。
  • 效果量 + 三態判定:不只看「是否顯著」，更要看效果多大；樣本小、CI 跨過門檻時應判 INCONCLUSIVE（無法斷定），不硬 pass/fail。
  • 非劣化檢定 (non-inferiority):有時目標不是「證明更好」，而是「證明不比舊的差超過某 margin」（CI 下界 ≥ −margin）。

19.5 混淆變數與可重現性（防自欺）

  • 混淆變數 (confounder / nuisance variable):與類別意外相關的「操作者可自由選的參數」（擷取視窗長度、來源主機、批次時間、韌體版本…）。若模型其實靠混淆變數而非真訊號分類 → 換環境就垮。防治:固定 / 隨機化（記種子）/ 多樣化 + held-out；並用「只有混淆變數」的對照模型檢查——若它也能分得不錯，代表有混淆。
    • 陷阱:「不適用 (N/A) 本身就是訊號」 — 某特徵剛好「對某類不適用」（如「播放時長 = N/A」≈ 非影音），模型學到的是這個捷徑而非行為。跨類比較時要排除或分層檢查。
  • 資料窺探 / p-hacking（研究者的自由度）:反覆看測試結果、回頭調特徵/門檻/模型直到分數好看 → 過度樂觀、不可重現。防治:看資料前先凍結協定（seed / fold / 指標 / 門檻）；測試集只用一次；看過結果再改 → 原結果失效，得用沒參與調整的新資料重跑（預先註冊 pre-registration 的精神）。

這正是本章開頭那句:先定義失敗、寫成可執行檢查、凍結，再採樣。

19.6 把驗證語義變成可強制的「契約」（ML 契約 vs API 設計）

19.1–19.5 講「什麼才算正確的驗證」；但文件寫了 ≠ 會被遵守。散文式規格可以描述語義，卻擋不下違反（散文不是機器可檢的條件）。ML 契約就是把這些語義變成機器可檢、違反即擋 (fail-closed)、且經簽核凍結的規則——它和一般 API 設計是不同層次的東西：

面向一般 API 設計ML 契約
管什麼介面:怎麼呼叫、欄位、型別、錯誤碼什麼資料 / 標籤 / 證據才有資格被相信、進訓練
「正確」＝欄位合法、型別對、存取成功（語法層）內容可信:label 語義對、樣本有效、分母對、無洩漏（語義層）
最危險的失敗型別錯、欄位缺（呼叫端立刻看得到）型別全對、也存進去了，但語義是錯的（表面成功、結論錯）
怎麼把關schema validation / API gatewayenforcement:違反語義條件 → BLOCK（fail-closed）
變更控制版本化freeze:owner 簽核 + 綁定 digest，語義變更要重簽

關鍵一句:欄位合法 ≠ 內容可信。 API 保證「格式對、傳輸成功」，但保證不了「這筆資料的意義是對的」。

實例（流量分類收資料）。 schema / API 要求每筆 capture 有 {duration: float, packets: int, avg_size: int, label: str}。某筆進來：duration=42.0、packets=3200、label="VOD"——型別全合法、成功寫入資料庫，API 契約完全滿足。但語義是錯的：這 42 秒其實整段是影片前的前置廣告，不是真正的 VOD 內容；這個 label="VOD" 是假的，拿去訓練會讓模型學到「廣告流量 ＝ VOD」。API validation 抓不到（欄位、型別全對）。ML 契約要多兩件 API 沒有的東西：

  • 可執行的語義驗收條件：capture 必須排除純廣告內容；capture_window_seconds 必須 ＝ 60（固定）；label 必須來自真實使用行為，不能只憑 DPI 認出應用程式就標記（例:認出 Teams 就標「通話」，但使用者並未通話）。任一不符 → BLOCK（在進資料集之前擋下，不是事後才發現）。
  • 凍結「可自由選的參數」清單：把擷取視窗、來源主機、批次時間、韌體版本等混淆變數（§19.5）列成 exact keys 並固定值；出現清單外的 key → BLOCK（防止有人偷偷多調一個變數把分數拉高、卻沒人知道）。

要不要用契約?一句話判準： 若兩個團隊都照同一份軟體規格 + API 文件實作，卻仍可能產出不同的 label、分母、PASS/BLOCK 或 training set，就代表設計文件不夠——必須先訂契約把語義釘死。ML 系統幾乎都符合這條件（語義分歧空間大），所以「評估要可信」光有 API 設計不夠。

契約不取代規格書 / API 文件，而是疊在其上，固定「什麼結果才正確、誰有權決定、證據不足時何時必須停」；衝突時的權威順序通常是 已簽核契約 ＞ 程式碼 ＞ 實作計畫 ＞ 舊報告 / 聊天。這正是把 19.1–19.5 的驗證嚴謹性，從「文件建議」升級成「上線前擋得下來的停止條件」。

契約給誰看?兩層、兩讀者——但都不是給模型看。

層給誰看內容權威
語義層（.md）人什麼才算正確、為什麼、裁示、誰決定、何時停owner 簽核 + 綁 digest（變更要重簽）
規則層（rules.yaml / schema）validator 程式exact keys、值域、門檻、BLOCK 條件由語義層衍生，供機器自動強制
  • 關鍵:讀契約的是「人」與「validator（一段確定性程式碼）」，不是 ML 模型。 模型不讀契約，只拿到被契約守住的乾淨、可信、已簽核的資料——契約治理的是「資料與流程」，不是模型內部。所以「給 AI 看」是常見誤會:它不餵進神經網路 / LLM，執行它的是普通驗證程式。
  • 為什麼要分兩層:「正確的定義」是人的領域判斷、無法自動推導（label 該怎麼標、哪些混淆變數要固定、門檻訂多少），所以語義層要人審、人簽、人負責；規則層再把它翻成機器可檢的條件，才能一致、大規模、違反即擋。業界兩傳統——YAML 為權威（機器檔權威、人看 description 欄）vs 散文 .md 為權威 + 另生機器規則；後者讓「為什麼算正確」由人扛、「有沒有做到」交機器查。

19.7 一句話

評估的可信度 = 驗證設計（分組 / held-out / nested CV，19.2）× 統計推論（CI / bootstrap / permutation，19.4）× 防自欺（控混淆、凍結協定、測試只用一次，19.5）。 模型分數高 ≠ 模型好；能通過這三關，才敢相信、才撐得起上線。要讓這三關真的擋得住，還得把它們寫成可強制、經簽核凍結的契約（§19.6）——否則只是文件建議。（資料面的來源可信度、採樣、漂移見 附錄 H；特徵選擇的穩定度見 附錄 I。）
